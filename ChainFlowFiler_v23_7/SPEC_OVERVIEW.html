ChainFlow Filer

フォルダを「開いて戻る」のではなく、横に流して並べるファイラー。 思考の流れをそのまま画面に残したまま、キーボードだけで作業を進めることを目的に設計されています。

Python 3.11 + PySide6 (Qt 6) Rust ネイティブコア (PyO3) Nuitka コンパイル配布 約 8,400 行 / 単一実行フォルダ 90 MB

Overview

これは何か

Windows 用のファイル管理アプリケーションです。エクスプローラーや一般的な2画面ファイラーの代替として、 大量のフォルダを行き来する作業を主な対象にしています。

中核にあるのは Miller Columns（macOS Finder のカラム表示）の考え方ですが、それを1列に限定せず、 複数の列を縦にも積める格子として扱う点が異なります。ここから「Chain Flow」という名前が来ています。

単体のアプリであると同時に、ChainFlow スイート（エディタ、検索、PDF、画像処理など11ツール）の 起点となるハブとしても機能します。ファイルを選んでコマンドを打つと、 そのパスを引き継いだまま各ツールが別プロセスで立ち上がります。

Concept

Chain Flow — 画面が思考の形になる

通常のファイラーでフォルダを掘ると、今どこにいるかは分かっても どう辿ってきたかは画面から消えます。戻るには履歴を遡るしかありません。

ChainFlow Filer は、フォルダを選ぶたびに右へ新しいペインを足していきます。 辿った経路がそのまま横一列に残るため、途中の階層に戻るのは「左のペインを見る」だけで済みます。

移動・選択・コピー・リネーム・プレビュー・ペインの追加と削除まで、 マウスを使わずに完結できるよう設計されています。ショートカットはアプリ全体で26種類が定義されています。

可搬性

Windows レジストリを一切使いません。セッション（session.json）、 お気に入り（favorites.json）、外部ツール定義（tools.json）は すべて実行ファイルと同じ階層に置かれます。フォルダごとコピーすれば別PCで同じ状態が再現されます。

特徴的な実装

フォルダショートカットの透過化 — Windows の .lnk がフォルダを指している場合、 表示名から拡張子を落とし、種類を「File Folder」として扱います。 ネットワーク上の深い階層にあるプロジェクトを、手元の「隣のフォルダ」として並べられます。

文脈ハイライト — Alt を押している間だけ、選択中ファイルの祖先フォルダが 上流のペインでハイライトされ、そこまでスクロールします。どの経路で今の場所に来たかが一目で分かります。

マーク — Alt+クリックで付けるマークはペインを跨いで保持されます。 複数のフォルダから集めたファイルをまとめて1回でコピー・移動できます。

配布構成について

Nuitka の --standalone でビルドし、Internal/ に実行ファイルと依存 DLL を格納、 その外にランチャーを置く構成です。単一 EXE ではありません。 Qt / Python の中核 DLL 約 62 MB を起動時に読み込むため、これを1ファイルに固めても速くはならないためです。

なお QtWebEngine（Chromium）は現在は使用していません。以前のバージョンで HTML プレビューに 採用していましたが、配布サイズが 640 MB に達したため取り外しました。

Performance

実測値と、その意味

「速い」を形容詞で語らないために、実測値を残しています。 以下は Windows 10 / Core i7 相当 / NVMe SSD、および 1Gbps LAN 上の SMB 共有での計測です。

項目条件改善前現行
タブの初回表示 ローカル 33,788 件 / 8ビュー 19,557 ms8,545 ms
タブ切り替え 同上・2回目以降 109 ms97 ms
ネットワーク表示 未訪問の SMB フォルダ・1行あたり 24.4 ms2.1 ms
起動（ウォーム） 2回目以降 —約 1.0 s
起動（コールド） OS 再起動後の初回 —約 3.5 s
常駐メモリ ワーキングセット —約 160 MB

速度を支えている3つの設計

1. 共有モデル — QFileSystemModel をアプリ全体で1つに絞り、 ペインごとにプロキシだけを持たせています。モデルを複数持つと監視スレッドが増殖します。

2. 一括ソート — 比較関数を1件ずつ Python で呼ぶのではなく、 フォルダの中身を Rust 側で一度だけ並べ、順位表を作って以降は整数比較だけで済ませます。 辞書のキーにはパス文字列ではなくモデル内部のノードID を使います （文字列にすると比較のたびにフルパスを組み立てることになり、33,788 件で約177万回の生成が発生していました）。

3. シェル API の回避 — Qt 標準の実装は「種類」列を得るために ファイルごとに Windows のシェル API を呼びます。ローカルでは 0.67 ms ですが、 SMB 共有では 46 ms かかります。ネットワーク上のパスに限り、 拡張子から種類名を組み立てる実装に差し替えています。

ネットワーク運用での注意

SMB 共有では、未アクセスのフォルダに初めて触るたびに約 126 ms かかります （一度触れば以降は OS のキャッシュにより 0 ms）。フォルダを次々に渡り歩く使い方とは相性が良い一方、 多数のフォルダを一度に走査する操作は重くなります。

また、共有サーバーが停止している状態では Windows の API が最大 27 秒 応答を返しません。 起動時とセッション保存時にこれを踏まないよう、ネットワークパスに対しては 存在確認を行わない実装にしています。

Limits

設計上の制約

説明の際に、できないことも併せて伝えられるよう記載します。

起動時間は約 1 秒を下回れない

Python と Qt のランタイム初期化に要する固定費で、アプリ側の最適化では削れません。これを短縮する唯一の方法は常駐化（プロセスを終了させない設計）で、現時点では未実装です。

巨大フォルダの初回表示は数秒かかる

33,788 件で約 8.5 秒。大半は QFileSystemModel による列挙とファイル情報取得で、Qt の内部処理にあたります。2回目以降は 100 ms 程度です。

ネットワーク上の「種類」表示が簡素になる

速度を優先した結果、SMB 共有上のファイルは JPG File のような表記になります（ローカルは Windows 標準の種類名のまま）。

Windows 専用

Qt 自体はクロスプラットフォームですが、シェル連携・ダークタイトルバー・ショートカット解決に Windows 固有の API を使用しています。
